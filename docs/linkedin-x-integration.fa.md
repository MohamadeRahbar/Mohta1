# مسیر اتصال لینکدین و X به محتوان

تاریخ بررسی: ۶ آبان ۱۴۰۵ — ۲۸ اکتبر ۲۰۲۶. این فایل نتیجه بررسی است؛ اتصال جدیدی فعال نشده و تنظیمات حساب‌ها تغییر نکرده‌اند.

## نتیجه

هر دو از طریق API رسمی و ورود با اجازه صاحب حساب قابل اتصال‌اند. استک فعلی Node.js مناسب است و بازنویسی لازم نیست. در کد فعلی، زیرساخت متن اختصاصی مقصد، صف، رسید ارسال و نگهداری رمزگذاری‌شده توکن وجود دارد؛ اما آداپتور انتشار لینکدین و X هنوز وجود ندارد.

## لینکدین

- **پروفایل شخصی:** ساخت Developer App، افزودن محصول Share on LinkedIn و درخواست اجازه `w_member_social` از صاحب حساب. این مسیر محصول سلف‌سرویس است. [راهنمای رسمی](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/share-on-linkedin)
- **صفحه شرکت:** مسیر Community Management و مجوز `w_organization_social`؛ حساب متصل باید نقش مجاز در صفحه داشته باشد. دسترسی این برنامه نیازمند بررسی لینکدین و احراز شرایط سازمان/صفحه است؛ تأیید آن تضمین‌شدنی نیست. [شرایط دسترسی](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/community-management-api-migration-guide)، [مجوزهای انتشار](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api)
- اجرای جدید با **Posts API** و نسخه پشتیبانی‌شده انجام شود؛ نمونه‌های قدیمی UGC مبنای اتصال جدید نباشند. انتشار متن، تصویر و ویدئو پشتیبانی مستند دارد. دریافت آمار و خواندن پست‌های شخصی را هم‌ارز اجازه انتشار ندانیم؛ مجوز خواندن شخصی محدود است. [Posts API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api)
- تمدید خودکار اتصال برای همه اپ‌ها تضمین نیست؛ Refresh Token برنامه‌ای به شرکای تأییدشده ارائه می‌شود. پنل باید انقضا و نیاز به اتصال مجدد را روشن نمایش دهد. [تمدید اتصال](https://learn.microsoft.com/en-us/linkedin/shared/authentication/programmatic-refresh-tokens)

## X

- ساخت اپ در Developer Console، فعال‌کردن ورود OAuth 2.0 با PKCE و درخواست حداقل مجوزهای انتشار/هویت. برای ارسال رسانه `media.write` و برای تمدید اتصال `offline.access` نیاز است. توکن عمومی App-only جای اجازه انتشار صاحب حساب را نمی‌گیرد. [ورود و مجوزهای رسمی](https://docs.x.com/fundamentals/authentication/oauth-2-0/authorization-code)
- انتشار از API ساخت پست و بارگذاری رسانه از مسیر رسمی انجام شود. [ساخت پست](https://docs.x.com/x-api/posts/create-post)، [بارگذاری رسانه](https://docs.x.com/x-api/media/upload-media)
- **هزینه دارد:** مدل فعلی خرید اعتبار و پرداخت به‌ازای مصرف است. تعرفه منتشرشده هنگام بررسی: ساخت پست معمولی **۰٫۰۱۵ دلار** و ساخت پست دارای URL **۰٫۲۰۰ دلار** برای هر درخواست. مثال: ۱۰۰ انتشار معمولی حدود **۱٫۵ دلار**؛ ۱۰۰ انتشار دارای لینک حدود **۲۰ دلار**، بدون هزینه سایر درخواست‌ها و مالیات. نرخ نهایی قبل از فعال‌سازی در کنسول کنترل شود. [تعرفه رسمی X](https://docs.x.com/x-api/getting-started/pricing)
- پیش از ارسال، برآورد هزینه و سقف مصرف داشته باشیم. خطای کمبود اعتبار باید از خطای شبکه و نتیجه نامشخص جدا باشد تا تلاش مجدد باعث انتشار تکراری یا هزینه بی‌دلیل نشود.

## اجرای محلی و دامنه

انتشار، درخواست خروجی به API پلتفرم است و به انتقال کل برنامه به هاست نیاز ندارد. بااین‌حال، **ورود OAuth به callback ثبت‌شده و مورد قبول سرویس نیاز دارد**؛ لینکدین در مستندات، callback HTTPS می‌خواهد و X تطابق دقیق آدرس را الزام می‌کند. پذیرش آدرس محلی را نباید فرض کنیم. پیش از اتصال واقعی باید مسیر HTTPS مناسب و محدود به callback تعیین شود. اکنون هیچ تونل یا دسترسی عمومی ساخته نشده است. [callback لینکدین](https://learn.microsoft.com/en-us/linkedin/shared/authentication/authorization-code-flow)، [callback در X](https://docs.x.com/fundamentals/authentication/oauth-2-0/authorization-code)

تا زمانی که برنامه محلی است، رایانه و سرویس محتوان باید هنگام انتشار زمان‌بندی‌شده روشن و به اینترنت متصل باشند.

## ترتیب پیشنهادی اجرا

1. تعیین مقصد لینکدین: پروفایل شخصی، صفحه شرکت یا هر دو؛ بررسی دسترسی اپ در هر سرویس قبل از وعده اتصال واقعی.
2. افزودن اتصال OAuth در تنظیمات: اتصال، قطع اتصال، نمایش حساب متصل و وضعیت انقضا؛ تفکیک کامل برندها و نگهداری کلیدها در بخش رمزگذاری‌شده موجود.
3. افزودن آداپتور متن و تصویر برای هر دو پلتفرم؛ استفاده از متن اختصاصی مقصد و صف فعلی.
4. اعتبارسنجی طول متن، قالب‌بندی و رسانه بر اساس قابلیت مقصد؛ بدون کوتاه‌کردن یا تبدیل خودکار پیام به چند پست بدون انتخاب کاربر.
5. ثبت شناسه و لینک پست، خطای قابل پیگیری، تمدید توکن و تلاش مجدد انتخابی؛ حفظ قاعده جلوگیری از ارسال دوباره مقصد موفق/نامشخص.
6. برای X: کنترل اعتبار، سقف هزینه و تفکیک پست دارای لینک در برآورد مصرف.
7. مرحله بعد: ویدئو، آمار، حذف و ویرایش؛ هر قابلیت فقط پس از بررسی مجوز و محدودیت همان API فعال شود. امکاناتی مانند پین را برای همه مقصدها یکسان فرض نکنیم.
8. آزمون با API شبیه‌سازی‌شده، سپس آزمایش واقعی مشخص و قابل بررسی روی حساب‌های متصل‌شده.

**پیشنهاد اجرایی:** شروع با انتشار در پروفایل شخصی لینکدین؛ هم‌زمان درخواست دسترسی صفحه شرکت در صورت نیاز. اتصال X بعد از مشخص‌شدن پذیرش هزینه API. این ترتیب، انتخاب پیشنهادی بر اساس مجوزها و هزینه‌های بالاست، نه محدودیت استک محتوان.

## اگر ساخت اپ در دسترس نباشد

اتصال می‌تواند شامل **صفحه شرکت و پروفایل شخصی** باشد. اگر ورود، ساخت یا تأیید اپ با محدودیت روبه‌رو باشد، علت دقیق باید از پیام خطای رسمی مشخص شود.

نکته اول: لینکدین حساب ورود جداگانه‌ای برای توسعه‌دهنده نمی‌خواهد؛ ورود به Developer Portal با همان حساب معمولی لینکدین انجام می‌شود. ساخت Developer App مرحله بعد از ورود است. بنابراین ابتدا باید روشن شود مانع، ورود به حساب است یا ساخت/تأیید اپ. [راهنمای رسمی دسترسی](https://www.linkedin.com/help/linkedin/answer/a526048)

اگر واقعاً امکان دریافت مجوز اپ مستقل وجود نداشته باشد، مسیر فنی جایگزین، اتصال محتوان به **API یک سرویس واسط** است؛ به‌جای درخواست مستقیم از LinkedIn API. مثلاً Buffer در مستنداتش هم انتشار در پروفایل شخصی و صفحه شرکت و هم API عمومی برای انتشار را پشتیبانی می‌کند. برای اتصال صفحه شرکت به Buffer، نقش Super Admin لازم است؛ پروفایل شخصی با اجازه خود صاحب حساب متصل می‌شود. [پشتیبانی لینکدین](https://support.buffer.com/articles/using-linkedin-with-buffer-K7tRkGD3mH)، [API عمومی Buffer](https://buffer.com/api)

طبق صفحه رسمی، دسترسی API در پلن Free هم وجود دارد و محدودیت مصرف به پلن وابسته است. **امکان ارائه سرویس به کاربر مستقر در ایران تأیید نشده است**؛ وجود این API به‌تنهایی تضمین رفع محدودیت جغرافیایی نیست. پیش از انتخاب یا پرداخت، دسترسی واقعی حساب و شرایط ارائه سرویس باید بررسی شود. [دسترسی و محدودیت API](https://buffer.com/api)، [شرایط سرویس](https://buffer.com/legal)

این مسیر وابستگی به واسط ایجاد می‌کند و همچنان نیازمند ساخت آداپتور در محتوان است. ارسال رسانه نیز به بررسی روش میزبانی نیاز دارد: API فعلی Buffer بارگذاری مستقیم فایل را پشتیبانی نمی‌کند، بنابراین فایل‌های صرفاً محلی را نباید قابل ارسال مستقیم فرض کنیم. [محدودیت‌های فعلی](https://support.buffer.com/en-us/articles/what-is-buffers-api-GtIYIQilz5)
